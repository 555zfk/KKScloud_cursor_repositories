# MuJoCo 工作区

机器人 URDF 导入 MuJoCo、做动力学仿真与数据分析的统一工作区。

## 快速开始

桌面上的 **MuJoCo 仿真器** 图标指向本目录的 `open_viewer.bat`。

- 双击图标：打开空窗口，可把模型文件拖进去
- 把模型文件拖到图标上：直接加载该模型

跑脚本用 `run.bat`，它会自动调用 MuJoCo 专属解释器：

```bat
run.bat scripts\inspect_model.py models\HU_M02_01\HU_M02_01_scene.xml
```

不带参数运行 `run.bat` 会列出所有可用脚本。

| `check_actuation.py` | 按 URDF 的 effort/velocity 判断哪些关节真装了电机，识别并联机构的被动输出端 |
| `controller.py` | HU_M02_01 的运动控制器：跑工况、实时可视化、导出关节载荷 CSV，见下节 |

| `build_scene.py` | 由 URDF 生成可仿真的 MJCF 场景：加地面、灯光、浮动基座、位置伺服（扭矩上限取自 effort），关闭自碰撞，并按 `loops.json` 闭合闭链、替换脚底碰撞体 |

| `test_sim.py` | 站立仿真测试，输出过程连拍图；`--fixed-base` 可锁死基座 |
| `test_motion.py` | 驱动测试：命令关节做正弦运动，检查伺服跟踪与力矩量级 |
| `check_install.py` | 环境自检：加载、步进、离屏渲染 |

## 用控制器跑工况

`scripts\controller.py` 是 HU_M02_01 专用的运动控制器。最简单的用法：

```bat
run.bat scripts\controller.py list                    列出所有工况
run.bat scripts\controller.py squat --view            开窗口看它蹲起
run.bat scripts\controller.py squat --depth 0.05      跑数据，不开窗口
```

**每跑一次，产物进一个带时间戳的独立目录**，终端上打出每个关节的载荷统计表：

```
output\HU_M02_01_walk_202608071650\      目录名 = 工况 + 运行时刻（到分钟）
    HU_M02_01_walk.csv                   每步一行的关节扭矩/转速 + 整机状态列
    HU_M02_01_walk.npz                   500 Hz 整机动力学全量，含世界系六维力
    HU_M02_01_walk.png                   六格连拍图
```

| 产物 | 给谁用 |
| --- | --- |
| `.csv` | 「关节需求计算」流程做 TN 曲线，**可直接喂，不用转换** |
| `.npz` | 「人形机器人本体设计流程」的 `wrench_decompose.py` 做六维力分解、倾覆力矩、轴承校核 |
| `.png` | 肉眼看动作对不对 |

**每次运行都是新目录，不覆盖任何东西。** 这条是踩过坑才定的：以前用固定文件名，
同一工况跑第二遍就把第一遍的 CSV 冲掉，而 npz 因为带了时间戳留了下来，结果 output
里躺着一堆对不上号的孤儿文件——有的运行只剩一个 npz，有的只剩一张连拍图。
按目录分组之后，一次运行的三份产物永远配对。

时间戳在**运行开始时取一次**，三份产物共用。分开取会出事：一次 100 步行走要跑将近
一分钟，CSV 和 npz 很可能落在不同的分钟里，就凑不成一组了。

npz 一次几十到几百兆（100 步那次 383 MB），只要 TN 数据时加 `--no-npz` 跳过。
给了 `--out` 的话按你指定的路径走，不再建目录。

### CSV 的整机状态列

排查行走问题主要看这几列：

| 列 | 含义 |
| --- | --- |
| `com_x` `com_y` / `ref_x` `ref_y` | 实测质心与规划质心，差值就是跟踪误差 |
| `base_roll` `base_pitch` `base_yaw` | 骨盆姿态。**行走失稳先看 `base_pitch`**，见坑 10 |
| `support` | +1 只有左脚踩地，−1 只有右脚，0 双支撑 |
| `clear_left` `clear_right` | 脚底板下沿离地高度，摆动相里贴到零就是蹭地 |
| `corr_pitch` `corr_roll` | 踝上的质心平衡修正量 |
| `att_pitch` `att_roll` | 髋上的骨盆姿态修正量 |
| `base_z` `grf_N` | 骨盆高度、地面反力 |

### npz 的字段与三个约定

字段名和布局照搬 `olilite_world_dynamics_v2`（`schema_version` 里写着），
也就是 `wrench_decompose.py` 的输入格式，**改完路径直接跑，不用转换**。
N 是帧数，nl=37 连杆，nj=33 关节（含浮动基座与 4 个球铰），na=24 执行器。

| 字段 | 形状 | 含义 |
| --- | --- | --- |
| `time` | (N,) | 时间戳，0.002 s 一帧 |
| `joint_wrench_world` | (N,nj,6) | **关节六维力**，`Fx,Fy,Fz,Tx,Ty,Tz`，世界系，力矩关于**关节锚点** |
| `joint_axis_world` | (N,nj,3) | 关节回转轴，世界系。倾覆力矩就是力矩里垂直于它的分量 |
| `joint_qpos` `joint_qvel` | (N,nj,7) (N,nj,6) | 关节位置/速度，按自由关节宽度对齐，短的补 NaN |
| `joint_position_world` `joint_quaternion_world_wxyz` | (N,nj,3) (N,nj,4) | 关节锚点位置、子体姿态 |
| `link_external_wrench_world` | (N,nl,6) | 各连杆受到的外力，**全部求和才是真实地面反力** |
| `link_parent_wrench_world` | (N,nl,6) | 父连杆施加的内力 |
| `actuator_output_torque` | (N,na) | 执行器实际输出扭矩，**已被 forcerange 削过** |
| `actuator_command_torque` | (N,na) | 削之前的指令扭矩。两者一拉开就是发生了截断 |
| `joint_actuator_generalized_force` | (N,nj,6) | 执行器广义力映射到各关节自由度 |

还有 `link_names` / `joint_names` / `actuator_names` 等名称表，以及
`motion_summary` / `motion_params` / `robot_mass_kg` / `xml_path` 等元信息。

写这个导出时有三个约定必须记牢，任何一个搞错下游全是错的：

1. **必须先调 `mj_rnePostConstraint`**，否则 MuJoCo 的 `cfrc_int`/`cfrc_ext` 里
   不含接触力和等式约束力。这台机的踝是并联闭链，等式约束力恰恰是大头。
2. **MuJoCo 原生是 (力矩, 力) 顺序，导出时翻成了 (力, 力矩)**，与
   `wrench_component_order` 一致。
3. **MuJoCo 的力矩参考点是 `subtree_com`，不是关节点**，导出时按
   τ_p = τ_c + (c − p) × F 搬到了关节锚点。不搬的话倾覆力矩会掺进一大项假的 r×F。

导出后按分析文档的三条判据校准过，全部通过：

- **力矩参考点**：膝的轴向投影对执行器扭矩 r=+0.9938（关于世界原点只有 −0.099），
  确认是关于关节点的。
- **地面反力**：全部 link 求和后静止段中位数 167.1 N，与整机重量分毫不差，且无负样本；
  只取脚踝则出现 0.44% 的负样本、低到 −8.7 N——就是文档警告的闭链污染，别用它。
- **四元数自洽**：把关节轴转到子体系得到 (0,1,0)，标准差 9e-17。

默认每个动作跑 30 秒。带 `--view` 时**动作结束后窗口不会自动关**：机器人会用 1.5 秒
平滑回到预备站姿站住，你可以继续拖动旋转查看。这时

- **按 R 重放一遍**（先点一下 3D 画面让窗口拿到焦点）
- **关掉窗口**脚本才退出

统计表和 CSV 在进入这个保持状态之前就已经输出了，不用等。重放只是给你看的，
不会覆盖已经统计并存盘的那一遍数据——想要新数据就重新跑命令。

> 重放能省掉每次重跑都要做的约 5 秒准备：并联踝传动标定、平衡反馈符号标定、
> 逆解建表这三步只在启动时做一次，重放直接复用。

### 六个工况的命令

先 `cd /d D:\WorkFiles\mujoco_ws`（`/d` 不能省，否则不换盘符）。
下面每条写的都是默认值，不写参数也是这个结果；加 `--view` 就开窗口实时看。

**站立** —— 原地不动，直腿。看静态载荷，基本没有扭矩。

```bat
run.bat scripts\controller.py stand
```

**蹲起** —— 双腿下蹲再起立，脚不动。目前最主要的选型工况，膝关节吃力最多。

```bat
run.bat scripts\controller.py squat --depth 0.05 --period 4
```

**左右重心转移** —— 骨盆左右平移，双脚不离地。单腿支撑的前置，看髋 roll 和踝 roll。

```bat
run.bat scripts\controller.py shift --amp 0.03 --period 4
```

**前后重心转移** —— 骨盆前后平移。看踝俯仰载荷和脚长方向的支撑余量。

```bat
run.bat scripts\controller.py lean --amp 0.03 --period 4
```

**摆臂** —— 双臂反相前后摆，下肢站着不动。看上肢模组载荷和摆臂对平衡的扰动。

```bat
run.bat scripts\controller.py armswing --amp 40 --period 2
```

**行走** —— 双脚交替离地。`--steps` 控制迈几步，`--length` 控制每步前进多少，
设成 0 就是原地踏步，`--steps 1` 就是抬一次脚放下（单腿支撑工况）。

```bat
run.bat scripts\controller.py walk --steps 1                    抬一次脚，单腿支撑
run.bat scripts\controller.py walk --steps 4                    原地踏步四步
run.bat scripts\controller.py walk --steps 20 --length 0.05     向前走约 1 米
run.bat scripts\controller.py walk --steps 100 --length 0.05    向前走约 5 米
```

最后一步总是并脚收势，所以 `--steps 20 --length 0.05` 前进的是 19×50 = 950 mm。

**走多远都行**。从第 14 步左右起步态进入稳定极限环，之后每一步的骨盆姿态、
质心误差、关节载荷全部逐周期重复。实测 100 步走 4949 mm，终点误差 1.5 mm，
统计量和 20 步那次一模一样。距离由 `--steps` 决定，不需要调别的。

忘了有哪些动作时 `run.bat scripts\controller.py list` 会打印出来。

### 常用参数

`--depth` 和 `--amp` 对位移类动作的单位是**米**（0.05 就是 50 毫米），对摆臂是**度**。

| 参数 | 含义 | 默认 |
| --- | --- | --- |
| `--depth` | squat 的下蹲量 m | 0.05 |
| `--amp` | shift / lean 的幅值 m，armswing 的摆幅 deg | 0.03 / 40 |
| `--period` | 一个来回的周期 s | 4（armswing 为 2） |
| `--duration` | 动作总时长 s，不含 settle | 30 |
| `--cycles` | 循环几次，给了就覆盖 `--duration` | 由时长折算 |
| `--stance` | 预备站姿的下蹲量 m | shift/lean 为 0.03，其余 0 |
| `--settle` | 进入预备站姿的时间 s，此段不计入统计 | 1.5 |
| `--view` | 开可视化窗口按实时速度播放 | 关 |
| `--out` | 指定 CSV 路径，npz/连拍图跟着放同一处，不再建运行目录 | 自动建目录 |
| `--no-strip` | 不出连拍图，跑得快些 | 出图 |
| `--no-npz` | 不导出六维力 npz（那份几十兆），只要 TN 数据时用 | 导出 |
| `--no-balance` | 关掉踝的质心平衡反馈，用来对比 | 开 |
| `--no-attitude` | 关掉髋的骨盆姿态反馈，用来对比 | 开 |

`shift` 和 `lean` 的 `--stance` **不能设成 0**。直腿锁死时腿没法变长，骨盆横移不出去，
逆解会留残差、两腿互相较劲，算出来的载荷是假的（见坑 7）。

`walk` 有自己一套参数，`--period` / `--cycles` / `--duration` 对它无效——总时长由
步数和各相时长算出来。`--stance` 在 `walk` 里表示全程预蹲量。

| 参数 | 含义 | 默认 |
| --- | --- | --- |
| `--steps` | 迈几步，最后一步是并脚收势；1 就是抬一次脚 | 4 |
| `--length` | 每步前进 m，0 为原地踏步，上限 0.06 | 0 |
| `--height` | 摆动脚抬高 m，下限 0.018 | 0.02 |
| `--t-ss` | 单支撑时长 s | 0.6 |
| `--t-ds` | 双支撑转移时长 s | 0.25 |
| `--squat` / `--stance` | 全程预蹲 m，越小膝越直越省扭矩 | 0.012 |
| `--inboard` | ZMP 相对支撑脚中心内移 m，越大越省横移行程 | 0.03 |
| `--first` | 先迈哪只脚 | left |
| `--arms` | 摆臂幅度 deg，0 为不摆 | 15 |

`--squat` 往小调是**免费的收益**：预蹲 30 mm 时膝要弯 57°、峰值扭矩 11.3 N·m（额定的
138%），压到 12 mm 后膝角 45°、扭矩 7.2 N·m（88%），连横向跟踪误差都从 20 mm 降到
13.6 mm。但下限卡在支撑腿的伸展余量上：单支撑时髋要横跨 36 mm、纵跨约一个步长，
步长 60 mm 时算下来至少要 6.2 mm，低于 5 mm 直接报错。

`--height` 反过来，**只能加不能减**。指令 20 mm 实测峰值只有 15.4 mm，摆动中段最低
贴到离地 1.6 mm——伺服柔顺加骨盆下沉吃掉了四分之一。降到 12 mm 必然蹭地绊倒，
所以低于 18 mm 直接报错。想要膝更直，减预蹲，别减抬脚。

也可以在 Python 里直接调，适合批量扫参数：

```python
from controller import Controller, Squat

c = Controller()                       # 标定只做一次，可反复跑工况
for d in (0.03, 0.05, 0.08, 0.10):
    c.run(Squat(depth=d, cycles=7.5)).report()
    c.save()                                    # 自动进 output\squat_<时间戳>\
    c.save(npz=False)                           # 扫参数时跳过几百兆的 npz
    c.save(f"output/squat_{int(d*1000)}.csv")   # 或者自己指定路径
```

`c.run_dir()` 拿本次运行的目录，想往里再塞自己的图或中间结果就用它。

开了窗口的话，在 `report()` / `save()` 之后调 `c.hold()` 把窗口留住并接管 R 键。

### 内部结构

控制器分三层，改哪一层要清楚：

1. **关节伺服**——不在 `controller.py` 里，而是场景 XML 的 `position` 执行器，
   由 `build_scene.py` 按各关节模组的 effort 算出 kp/kv 与扭矩上限。
   改伺服增益要回去改 `build_scene.py` 再重新生成场景。
2. **轨迹生成**（`Trajectory`）——把工况变成"每个时刻各关节该到哪、质心该在哪、
   哪只脚踩着地"。两条实现：
   - `PostureTrajectory`：双脚不离地的工况。基座沿一条轴走，`PostureTable` 离线
     解成一维位移查表，仿真时插值。
   - `WalkTrajectory`：行走。`gait.py` 给出质心和双脚轨迹，逐帧全身逆解成关节角。
3. **反馈**——两路并行，管的是**两件不同的事**，缺一不可：
   - `Balance`：踝策略 PD，把**质心位置**拉回计划位置。`--kp-bal` / `--kd-bal` / `--bal-limit`。
   - `Attitude`：髋 PD，把**骨盆姿态**拉回水平。`--kp-att` / `--kd-att`。
     质心反馈看不见姿态，见坑 10。

工况（`Motion` 子类）通过 `trajectory(robot)` 交出一条轨迹。双脚不离地的工况只要
实现 `u(t)` 或 `arms(t)` 就够，基类会包成 `PostureTrajectory`；`Walk` 自己返回
`WalkTrajectory`。加完登记到 `MOTIONS`。

行走的规划链在 `gait.py`，四步：

1. **落脚点**——按步长排出每步的落点，最后一步并到支撑脚旁边收势。
2. **ZMP**——单支撑时钉在支撑脚底板中心（再往内挪 `inboard`），双支撑时线性过渡。
3. **DCM**——ξ = x + ẋ/ω 满足 ξ̇ = ω(ξ − p)。从"最后停在双脚中点"**倒推**每一相的
   ξ 初值。必须倒推：正推要猜初始质心速度，猜错就发散；倒推是收敛的，前面各相的
   误差被 e^{−ωT} 指数压掉，起步 ξ 自然落到双脚中点，和静止站立的实际状态对得上。
4. **质心**——按 ẋ = ω(ξ − x) 积分。摆动脚水平走五次多项式、竖直走升余弦。

### 能力边界

走的是**离线规划 + 时间参数化回放 + 两路反馈收残差**。规划不看实测状态，所以能做既定
步态（原地踏步、直线行走），做不到受扰恢复、实时改落脚点、上下坡——那要 MPC/WBC
一类的在线全身控制器。

这台机上实测出来的可用范围（预蹲 12 mm、抬脚 20 mm、单支撑 0.6 s）：

| 项 | 结果 |
| --- | --- |
| 步长 50 mm | 干净，终点误差 1.5 mm，横向误差 13.6 mm，无截断 |
| 步长 60 mm | 干净，终点误差 1.2 mm，膝峰值 8.2 N·m |
| 步长 70 / 80 mm | **摔倒** |
| 抬脚 20 mm | 干净。实际只抬起 15.4 mm，摆动中段离地 1.6 mm |
| 抬脚 15 mm | 勉强不倒，但横向误差飙到 143 mm |
| 抬脚 12 mm | **摔倒**——蹭地绊倒 |
| 预蹲 8~20 mm | 都干净，越浅膝扭矩越低、跟踪越好 |
| 预蹲 30 mm | 20 步能走，**40 步摔倒**；膝扭矩已超额定 38% |
| 步数 20 / 40 / 60 / 100 步 | 全部干净，终点误差恒为 1.5 mm，**误差完全不累积** |
| 单支撑 0.45 / 0.6 / 0.8 s | 都能走，0.45 s 的横向跟踪误差反而最小 |
| 关掉踝的质心反馈 | 仍能走完，终点差约 27 mm |
| 关掉髋的姿态反馈 | 走 14 步后**摔倒**（见坑 10） |

倒数第二行值得注意：前馈轨迹本身就基本对，质心稳定器主要在收残差。这是平地 + 模型与
规划完全一致的结果，真机上模型误差和地面不平会让这个结论反过来。

最后一行相反——姿态反馈**不是可选项**，没有它走不远。

100 步那次尤其说明问题：4949 mm 的终点误差和 20 步时一模一样，因为从第 14 步起
步态已经收敛成稳定极限环（骨盆 pitch 锁在 0.49°、roll ±0.88°、横向误差 6 mm，
逐周期完全重复）。距离本身不是约束，能不能进极限环才是。

## 十个必须知道的坑

### 1. MuJoCo 打不开含中文的路径

MuJoCo 底层用 C 的 `fopen` 读网格，Windows 上按系统 ANSI 代码页（本机 cp936）解释路径，
收到 UTF-8 的中文就报 `Error opening file`。

解决办法是把原始导出包整个复制到本工作区（路径全为 ASCII）。各模型的 `src\` 就是这样的副本，来源分别是

```
HU_M02_01  D:\WorkFiles\2026.6\mini预研外观样机URDF制作\HU_M02_01_URDFfiles
HU_M01_01  D:\WorkFiles\2026.4\Oli nano设计规划\初版整机URDF制作\HU_M01_01_URDFfiles
HU_D03_01  D:\WorkFiles\2025.5\531版本URDF模型导出\hud0302_description_521下午6点\hud0302_description_521_6
```

副本与源彼此独立：本工作区不再依赖原始文件夹，源目录改名、移动、删除都不影响仿真。
代价是**在 SolidWorks 里重新导出 URDF 后，必须手动重新复制一次**，否则这边用的还是旧网格。

> 另一种做法是用 `mklink /J` 建目录联接（指针），不占空间且自动同步，
> MuJoCo 访问 ASCII 的联接路径、中文由文件系统驱动层处理，同样可行。
> 本工作区选择了副本方式，换取与源目录解耦、可整体打包转移。

### 2. 碰撞网格必须自己处理

MuJoCo 对网格碰撞取**凸包**。sw2urdf 的碰撞网格直接复用全分辨率外观件，
关节壳体这类包裹型零件取凸包后变成实心块，会把相邻连杆整个吞进去——
本模型初始姿态曾出现 23 处自碰撞、最深穿透 50.8 mm、接触力达整机重量的 150 倍。

`build_scene.py` 的处理是关闭自碰撞（机身 `contype=1/conaffinity=0`，
地面 `contype=0/conaffinity=1`），只保留机身与地面的接触。这对关节扭矩需求分析是标准做法。
若后续需要真实的自碰撞检测，必须手工用长方体/胶囊体重建碰撞图元。

**脚底要单独处理**。踝部壳体和脚板同属一个连杆，取凸包后接触点位置和落地冲击都不可信。
在 `loops.json` 的 `soles` 里列出脚部连杆，脚本会取该连杆网格最低 15 mm 内顶点的轮廓，
生成一块 8 mm 厚的贴地 box 并把原网格设为纯视觉。HU_M02_01 得到 136×80 mm 的脚印、
4 个规整支撑角点——换上之后整机从"3.3 秒后倾倒"变成 10 秒静止不动。

### 3. URDF 无法表达闭链

三个模型的踝部阿基里斯拉杆、以及 HU_D03_01 与 HU_M01_01 腰部的推杆，
在 URDF 里都是断开的悬空分支——URDF 只能描述树状结构，表达不了闭链。

闭合方法（`build_scene.py` 按 `loops.json` 自动完成，HU_M02_01 / HU_M01_01 已配好）：

1. **补球铰**。sw2urdf 把拉杆与曲柄之间的球铰导成了 `fixed`，支链整条是刚性的。
   在支链根部加一个 `<joint type="ball">`，否则下一步的约束会把机构锁死——
   刚性杆 + 点约束会让 6 个约束方程去解 4 个自由度，超定。
2. **加 connect**。`<equality><connect body1="末端连接点" body2="目标连杆" anchor="0 0 0"/>`。
   MJCF 里 anchor 按 body1 的局部坐标给，body2 一侧的对应点由参考位形自动算出，
   所以零位残差天然为 0。
3. **收紧约束阻抗**。默认阻抗下球铰会被拉开几毫米，受力分析不能接受。
   用 `solref="0.004 1" solimp="0.99 0.9999 0.0001 0.5 2"`（timeconst 取 2×timestep 保稳定，
   dmax 拉到 0.9999 把约束做硬）后，HU_M02_01 的残差从 4.3 mm 降到 0.09 mm。

球铰会多出一个"杆绕自身轴自转"的冗余自由度，无物理影响但需要阻尼，
脚本用单独的 `rodball` 默认类给它 `damping=0.01`、`armature=1e-6`——
不能套电机那套 `armature=0.01`，否则几十克的拉杆会重得离谱。

没配 `loops.json` 的支链，`build_scene.py` 不会给它建驱动器，并打印警告：
悬在空中的杆，其载荷数据没有意义。

### 4. 零质量连杆会让编译直接失败

MuJoCo 要求可动连杆（父关节非 fixed）的质量和惯量大于 `mjMINVAL`，否则报
`mass and inertia of moving bodies must be larger than mjMINVAL`。
SolidWorks 里没赋材质的零件导出后质量就是 0。

HU_D03_01 的 `waist_yaw_link` 曾是如此（已按实测值补全，见下文）。`convert_urdf.py`
默认给这类连杆补 1 g 的名义质量让流程能跑通，但**正确做法是回 SolidWorks 取实测值
或赋材质后重新导出**，否则该连杆的质量和惯量在仿真里是假的。
导入前先跑 `check_inertial.py` 排查。

### 5. 移动副（prismatic）不能和转动副混着处理

带电动缸/丝杠的腰部或踝部会导出成 `prismatic` 关节，MuJoCo 里是 `slide` 类型，
量纲和转动副完全不同：行程单位是 m 不是 rad，位置伺服的 `kp` 单位是 N/m 不是 N·m/rad。

HU_M01_01 是第一台带移动副的模型，暴露了脚本里的三处问题，均已修复：

- `build_scene.py` 原先直接跳过非 hinge 关节，移动副既不建驱动器也不进被动清单，是隐性遗漏
- `inspect_model.py` 把 slide 的行程按弧度换算成度，−10~+25 mm 显示成了 [−0.57°, +1.43°]
- `test_sim.py` 用 `qpos[7:]` 的下标去查关节名，与关节 id 差一位（浮动基座占 7 个 qpos），
  报出来的"偏离最大的关节"一直是错的

### 6. 哪些关节有电机，要看 effort 而不是名字

并联机构里，**被动输出端和主动输入端很容易搞反**。HU_M02_01 就踩过：
按名称启发式（`achilles` 一律当被动）建出来的场景，驱动了 4 个物理上没有电机的
踝 pitch/roll，却把 4 个真电机（阿基里斯曲柄，12 N·m / 14.56 rad/s）当成了被动件。
这样算出的踝部扭矩需求完全不能用。

可靠信号是 URDF `<limit>` 里的 `effort` 和 `velocity`：被动输出端填 0，
主动输入端填模组额定值。`check_actuation.py` 就是按这个列表判断的，`build_scene.py`
也据此建驱动器，并把 `forcerange` 设成 ±effort——没有扭矩上限的话，
控制器能输出任意大扭矩，选型需求会虚高（这正是设计流程里的结构性风险 1）。

两点例外要留意：

- **effort 被统一填成同一个值时该数据无效**。HU_D03_01 给所有关节都填了 45 N·m / 16 rad/s，
  据此无法分辨主被动，只能人工核对。
- **支链末端悬空时不能建驱动器**。判据是"该关节子树的所有末端都是未闭合的 `_cp_` 连杆"——
  只看末端而不是整个子树，否则膝关节这种下游挂着悬空支链的会被误判成被动。

### 7. 锁着膝盖做不出任何水平移动

直腿站姿下想把骨盆横移 30 mm，逆解一定收敛不了。原因是纯几何的：
髋到踝的距离要从 h 变成 √(h² + 0.03²)，即**腿必须变长约 0.75 mm**，
而直腿已经是这条腿的最大长度（膝角无论正负偏离零位都只会让腿变短）。

这个坑很隐蔽，因为**症状看起来像数值问题**。第一次跑横移时残差 70.87 mm，
像是求解器没收敛；换成自适应阻尼的 Levenberg–Marquardt 后降到 1.12 mm，
看着"快好了"——其实那 1.12 mm 就是够不着的部分，再怎么调求解器也消不掉。
判断依据是残差不随迭代次数下降。

后果不只是残差：两条腿都在够一个够不到的目标，就会通过地面互相较劲，
凭空造出假载荷。当时报出膝关节峰值 19.7 N·m、p99 达额定的 199%，
而正确解只有 6.8 N·m——**差了三倍，方向还是"超限"，足以误导选型**。

解决办法是物理的不是数值的：**水平移动的工况必须先微蹲**。`Motion.stance`
就是干这个的，`shift` / `lean` 默认预蹲 30 mm，加上之后残差归零。真机同理，
人做重心转移前也会本能地屈一点膝。

顺带记两条求解器经验：

- 直腿附近雅可比条件数能到 **1e19**，因为膝角对脚高的影响是二次的、
  在直腿处导数为零。定值阻尼在这里要么迈不动步、要么解出巨大步长被截断后来回震荡，
  所以 `_solve` 用按误差是否下降来自适应调整阻尼的 LM。
- 蹲起工况能收敛是因为它在第二个采样点就给膝一个 8° 的初始弯曲，很快离开奇异区；
  横移全程贴着直腿走，正好一直踩在坑里。

### 8. 支撑腿切换时，平衡修正不能跟着阶跃

踝策略的修正只该加给踩着地的脚——摆动脚在空中，给它加修正改变的是落地瞬间的脚板
姿态，本该平贴地面的脚会带着角度砸下去。但**"哪只脚在支撑"本身是阶跃的**，
修正直接按它开关，等于给踝伺服一个角度阶跃。

第一次跑单腿支撑时的症状：**摆动腿**的 `left_achilles_A` 报出 12.00 N·m，正好顶到
峰值截断，而那条腿明明悬在空中。落地冲击也被带高到 268 N（1.6 倍体重）。

修正办法是权重连续化。`gait.load_at()` 给每只脚一个 0~1 的"踩地权重"，在离地前和
落地后各留 0.12 s 的升余弦过渡（必须短于双支撑时长，过渡才发生在脚还踩着地的时候）。
改完摆动腿曲柄峰值降到 2.42 N·m，落地反力降到 226 N。

**空中的肢体报出接近满量程的载荷，一定是控制指令不连续，不是真载荷。**

### 9. 并联踝的曲柄行程要同时装下俯仰和横倾

串联踝的 pitch 和 roll 各有各的行程，互不占用。并联踝不是——两个曲柄的角度是
pitch 和 roll 的线性组合，**两个方向共用同一份行程预算**。

HU_M02_01 的曲柄行程是 −40°~+20°，看着和踝 pitch 的 −40°~+20° 一样宽，
实际可用区域是一个被斜切的平行四边形。40 mm 预蹲要 −29° 俯仰，行走的横倾再要 −9°，
按传动矩阵折算过去曲柄要转到 −40.5°，**刚好越界**。终端会报
`指令超出限位被截断: ['left_achilles_A']`。

预蹲降到 30 mm 后曲柄最深只到 −36.3°，留出了横倾的余量；现在默认的 12 mm 预蹲
只要 −22.7° 俯仰，余量很宽。同样的机制也是大步长报截断的原因——迈得越远，
蹬离和触地要的踝俯仰越大。

**排查方法**：截断警告说的是位置指令越限，不是扭矩越限，别去看扭矩表。
用 `ParallelAnkle.jac` 的逆矩阵把 (pitch, roll) 折算成曲柄角，和曲柄限位比。

### 10. 质心反馈看不见躯干姿态，行走会一路前倾到翻倒

规划全程要求骨盆保持水平，但**骨盆是自由体，没有任何执行器管它的姿态**。行走时
每次落地都往身体上打进一个前倾角冲量，没有反馈就只能累积。

实测：每步涨约 0.4°，一路 0.11 → 0.25 → 0.34 → … → 4.23 → 5.15 → 8.03°，
到第 14 步失控，第 15 步翻倒。20 步以内的短距离测试完全看不出来，所以这个坑
是在把步数从 12 加到 20 时才暴露的。

**最要命的是质心反馈完全看不见它**。翻倒前一刻质心位置误差还只有几毫米——身体是
**绕着质心**在转，质心位置这个量里不含角动量信息。只盯着 `com_x/com_y` 调参数，
永远调不出问题在哪。排查行走失稳，第一个要打印的是基座四元数换算出的 roll/pitch。

修正办法是加一路独立的姿态 PD（`Attitude` 类），测骨盆倾角、反馈到**髋**：

- **用髋不用踝**。踝已经被质心反馈占着，而且单支撑时踝力矩受脚板尺寸封顶；
  支撑脚踩死在地上时，髋 pitch/roll 直接就是躯干相对大腿的角度，权限最高。
  标定实测髋 pitch 对骨盆 pitch 的传递比是 −0.98 rad/rad，几乎是 1:1。
- **同样要按踩地权重分配**，理由同坑 8——加给摆动腿只会改落脚点。
- **增益不能大**。kp=1.0 收敛到稳态前倾 0.7°；kp=1.5 就过冲，第 10 步反而摔。
- 骨盆 roll 方向的传递比只有 −0.13（双脚同时着地时互相约束住了），权限弱得多，
  好在 roll 本来就不累积，一直在 ±1.6° 内摆。

加上之后走 100 步（4949 mm）终点误差还是 1.5 mm，骨盆 pitch 稳在 0.49°。

## HU_M02_01 模型现状

37 连杆、28 转动关节、总质量 17.029 kg、包围盒 0.399 × 0.477 × 0.995 m。
场景补上并联踝闭链后 `nq=51`、`nv=46`、`neq=4`、24 个位置伺服、4 个被动踝关节。

已验证：**10 秒站立静止**——基座下沉 2.7 mm、末段速度 0.0000 m/s、
地面反力 167.1 N 与整机重量完全吻合、8 个脚底支撑点、关节最大偏离 0.75°。

### 并联踝（已闭合）

踝 pitch/roll 没有电机，由小腿上两个 12 N·m 的阿基里斯曲柄经拉杆驱动。
几何：曲柄臂 22 mm 绕 x 轴、A 杆 146 mm（曲柄在小腿 z=−0.064）、
B 杆 98 mm（z=−0.112），两连接点在脚板上 y=±22 mm、踝心后方 21.7 mm。
两曲柄臂分别指向 ±y，所以**共模转动出侧倾、差模出俯仰**：

```
侧倾 ≈ 0.91 × (θA + θB) / 2
俯仰 ≈ 0.79 × (θA − θB) / 2
```

实测（锁基座、关重力、connect 残差 < 0.09 mm）：θA=θB=20° → 侧倾 18.21°；
θA=20°、θB=−20° → 俯仰 15.89°、侧倾耦合 1.71°。

两个曲柄的限位是**镜像**的：A 为 [−40°, +20°]，B 为 [−20°, +40°]。组合起来
踝俯仰可达 −31.6° ~ +15.8°，比踝关节自身的限位 [−40°, +20°] 更窄，
也就是说**行程由曲柄决定，踝的限位是永远碰不到的机械硬止点**。

### 蹲起工况载荷（下沉 50 mm，周期 4 s，2 个循环）

```bat
run.bat scripts\controller.py squat --depth 0.05 --period 4 --cycles 2
```

跟踪 51.7 mm / 指令 50 mm，地面反力 162.6 ~ 175.0 N（重量 167.1 N），两个循环不倒。

最吃力的是膝关节（mini4310，额定 8 / 峰值 40 N·m）：峰值 7.51 N·m、p99 7.44、RMS 5.09。

**三个数各有各的判据，不能混着看**：

- 瞬时能力看峰值：7.51 / 40 = **19%**
- 热负荷看 **RMS 对额定**：5.09 / 8 = 64%，而发热正比于扭矩平方，
  实际热负荷是连续极限的 **41%**
- p99 是选型时"能不能出得来这个力"的判据，7.44 N·m 仍低于额定 8 N·m

三条都通过，**这个深度的蹲起对膝关节模组余量充裕**。其余关节更宽松：
阿基里斯 p99 最大 0.67 N·m（额定 3.5，19%）、髋 pitch 0.66 N·m（8%）。
转速全部低于额定的 12%，这个工况完全是扭矩受限。

> 别拿这个结论外推。下沉量加倍到 **100 mm 就越线了**：膝角 83.0°，膝峰值 10.22 N·m、
> p99 10.13（额定的 127%）、RMS 7.02（热负荷 77%）——p99 已进过载区，热负荷也逼近上限。
> 单腿支撑时单腿承重翻倍，量级同样在额定之上。这两个工况才是膝关节选型的决定性场景。

膝关节扭矩可以手算校核：单腿承重 83.5 N，膝相对踝前移 L2·sin(27.4°) = 96.6 mm，
静力矩 83.5 × 0.0966 = 8.07 N·m，与仿真的 7.5 N·m 量级一致。

三个实现要点，换机型时同样适用：

- **平衡反馈不能省**。纯开环回放姿态时，第一个循环还行，第二个循环踝部误差累积到
  −22.8°（指令 −15°）就翻倒。加一层"质心偏离支撑中心 → 修正踝角"的踝策略后，
  下沉跟踪误差从 9 mm 降到 0.8 mm，阿基里斯峰值扭矩反而从 4.5 N·m 降到 1.7 N·m——
  姿态对了就不用互相较劲。反馈符号由脚本启动时实测标定，不写死。
- **逆解要约束脚板完整的 6 维位姿**。腿正好 6 个自由度。只约束 x/z/俯仰的话，
  倾斜的髋 pitch 轴会让脚在偏航上扭动，凭空造出髋 roll 8.08 N·m、髋 yaw 5.08 N·m 的
  假载荷；补齐 6 维约束后分别降到 0.59 和 0.55 N·m。
- **标定并联传动时要先关掉摩擦、把伺服调硬**。用正常增益驱动曲柄测出来的是
  "含伺服柔度与库仑摩擦死区"的响应，不是运动学传动比：左右腿几何明明是精确镜像，
  量出来的增益却差 20%，连带蹲起时左右膝载荷差 40%。标定副本里把 `dof_frictionloss`
  清零、`actuator_gainprm` 放大 50 倍后，左右偏差降到 3.2%，踝部跟踪误差从 3° 降到 0.06°，
  阿基里斯峰值扭矩从 2.37 N·m 降到 0.67 N·m。脚本会自动打印左右偏差，超过 3% 就提示。

顺带一个设计上的发现：因为髋 pitch 轴是倾斜的（0, 0.94, −0.342），
**保持脚板水平的下蹲需要髋 yaw 转 ±10.34°、髋 roll 转 ∓3.13° 来配合**，
这不是控制误差而是这套髋部构型的运动学要求。

### 重心转移工况（预蹲 30 mm，幅值 ±30 mm，周期 4 s）

```bat
run.bat scripts\controller.py shift --amp 0.03
run.bat scripts\controller.py lean  --amp 0.03
```

预蹲 30 mm 对应髋 pitch −24.9°、膝 +44.8°、踝 pitch −21.2°。横移 ±30 mm 时
髋 roll 摆 −1.9°±4.1°、踝 roll 摆 ±4.6°；前后移则主要吃踝 pitch（±4.6°）。

| | 膝 峰值/RMS | 髋 roll 峰值 | 阿基里斯 峰值 |
| --- | --- | --- | --- |
| shift ±30 mm | 6.79 / 5.58 | 2.53 | 1.41 |
| lean ±30 mm | 6.49 / 5.28 | 0.95 | 2.13 |

**这两个工况里真正的载荷来自预蹲本身，不是移动。** 膝的峰值与 RMS 几乎相等
（6.79 对 5.58），说明它承的基本是保持屈膝站姿的恒定载荷；横移带来的增量只有
1 N·m 出头。热负荷因此达到额定的 42~49%，比动作幅度大得多的蹲起（34~40%）还高——
**屈膝待命的静态功耗才是膝关节模组的主要热源**，这一条对续航和散热设计的意义
大于任何单次动作的峰值。

上肢摆动（±40°、周期 2 s）肩 pitch 峰值 0.70 N·m、转速 2.19 rad/s（额定的 18%），
是全部工况里唯一转速占比上双位数的关节；腰 yaw 受反相摆臂的反作用只有 0.15 N·m。

> 正弦轨迹要平滑起振。`sin` 在 t=0 处位移为零但速度不为零，直接开跑等于给伺服一个
> 速度阶跃，会造出一个单点尖峰：摆臂工况原本报肩 pitch 峰值 4.98 N·m，而 p99 只有
> 0.65——差 8 倍就是这么来的。`Motion.ramp()` 用半个周期的余弦包络起振后峰值回到 0.65。
> **峰值与 p99 差一个数量级时，先怀疑是数值假象而不是真载荷。**

### 行走工况载荷（预蹲 12 mm，抬脚 20 mm，单支撑 0.6 s，双支撑 0.25 s）

```bat
run.bat scripts\controller.py walk --steps 1                    抬一次脚
run.bat scripts\controller.py walk --steps 4                    原地踏步
run.bat scripts\controller.py walk --steps 20 --length 0.05     前进 950 mm
```

单位 N·m，取统计区间内的峰值 / p99；括号里是 p99 占额定的比例。三个工况都无截断。

| 关节 | 抬一次脚 | 原地踏步 | 前进 50 mm/步 | 额定 |
| --- | --- | --- | --- | --- |
| 膝 pitch | 6.2 / 6.1 (77%) | 6.7 / 6.6 (83%) | 7.2 / 6.9 (87%) | 8 |
| 髋 roll | 13.9 / 13.2 (165%) | 13.8 / 13.0 (162%) | 13.8 / 12.8 (160%) | 8 |
| 髋 pitch | 2.2 / 1.8 (23%) | 2.2 / 2.0 (25%) | 5.4 / 5.0 (63%) | 8 |
| 髋 yaw | 3.3 / 3.0 (38%) | 3.4 / 3.4 (42%) | 3.2 / 3.0 (37%) | 8 |
| 阿基里斯 | 4.6 / 4.2 (121%) | 4.5 / 4.2 (119%) | 4.8 / 4.7 (134%) | 3.5 |
| 肩 pitch | 0.1 | 0.1 | 0.6 / 0.5 (7%) | 8 |

**髋 roll 是这台机走路的瓶颈，而且改步态救不了。** 单支撑时髋 roll 轴承的力臂就是
髋半宽 75 mm：整机 17.03 kg 里髋以上约 14 kg，14 × 9.81 × 0.075 ≈ 10 N·m，加上动态
分量就是实测的 13.8。这个数**与预蹲深度、步长、ZMP 内移量都无关**——质心跟着骨盆走，
无论骨盆横移多少，质心到支撑侧髋轴的横向距离恒等于髋半宽。想降只能改机械：缩窄髋宽，
或换更大力矩的髋 roll 模组。

三个工况的髋 roll 峰值几乎一模一样（13.9 / 13.8 / 13.8），正是这个结论的实证：
**只要有单腿支撑，就是这个数。** 把预蹲从 30 mm 压到 12 mm 也只让它从 14.8 降到
13.8，进一步印证了力臂由髋宽决定、和姿态无关。

热负荷这边反而宽裕：单支撑占空比 20~73%，髋 roll 的 RMS 是 4.7~6.1 N·m，
热负荷 39~58% 额定。所以是**短时过载问题，不是过热问题**——要核对的是模组的
TN 曲线和过载时长曲线，而不是连续功率。

**膝 pitch 靠减预蹲救回来了。** 预蹲 30 mm 时膝 p99 是 11.0 N·m（138% 额定），
压到 12 mm 后降到 6.9（87%），退回额定以内。原因是大腿小腿各只有 200 mm，
膝角随预蹲量按开方涨，30 mm 就要弯 45°、力臂拉得很长。阿基里斯曲柄仍在
120~135% 额定，是并联踝那对 mini3407 的普遍性问题，减预蹲只把它从 153% 降到 134%。

> 落地冲击的地面反力峰值 205~230 N（整机重量 167 N，约 1.2~1.4 倍）。这个数
> **不能当定量结论**：接触刚度/阻尼用的是 MuJoCo 默认值，没有按真实脚底材料标定。
